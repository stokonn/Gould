# Gould 0.14 development architecture

**Status:** implementation branch; unreleased. This document describes the current branch and its remaining verification limits.

## Boundaries

The Android application remains in `:app` and owns Compose screens, Android ViewModels, Room, widgets, audio, microphone services, notifications, WorkManager and file access. `:activity-domain` is a Kotlin Multiplatform module with deterministic week, goal, classification, streak, Freeze and aggregate rules in `commonMain`; it declares and validates a JVM target. Android remains the only application platform in this update; no iOS app or cross-platform persistence is included.

PracticeCoordinator and PracticeEngine remain authoritative for practice timing and session completion. Activity reads valid existing sessions through their recorded practice day/time zone and adds separately typed manual entries. It does not create or rewrite PracticeSession rows. Manual entries are accepted for today and the previous two local calendar dates, including dates before Activity was first opened. UI and repository validation use the same local-date window; the repository resolves today's date and zone at submission. New activity dates use local Monday-first calendar weeks; observed week records retain their zone. Rules accept dates/zone metadata explicitly rather than reading the global clock.

## Progression and durability

Historical goal rows take effect on a Monday. Weeks are projected chronologically; daily inactivity receives the Day Off allowance in ascending date order, then Miss. Day Off is a calendar label for unused session allowance; it neither consumes nor grants a Freeze. A Freeze protects a closed week that failed its configured weekly requirements. Weekly streak success depends on the configured session goal and optional minutes goal, separately from daily labels. Beta Week suppresses official streak processing and the first-partial-week Freeze milestone. Freeze and longest/current streak state are recalculated from source activity, avoiding duplicate consumption on repeat evaluation or historical correction. Global daily streak and duration totals use the same combined session/manual workout projection as Activity; source IDs prevent duplicate rows, while separate workouts on one date remain distinct.

Every eligible perfect week that meets its configured session goal and optional minutes goal earns its own durable cosmetic grant, including Beta Week. Beta Week grants no official streak success and does not advance the Freeze milestone. The four-consecutive-success official Streak milestone is separate: it adds one Streak Freeze and never gates or replaces a weekly cosmetic. A broken streak resets only Freeze milestone progress without removing earned or pending cosmetic grants. Reward evaluation scans earlier weeks so eligible weeks missed by the prior minutes-only condition are recovered. Grants are keyed to their eligible week and do not create ownership. The Activity Weekly Goal section shows Locked, Claim, or Claimed from persisted state; Claim atomically inserts ownership and records its timestamp in `acknowledgedAt`. Pending cosmetic IDs are reserved across weeks. Previously owned rewards are treated as claimed, not offered again. The collection remains available from Profile, where owned cosmetics can be applied. The catalog centralizes item IDs, categories, rarity weights and unlock descriptions; current weights are Common 60, Rare 25, Epic 12 and Legendary 3. If no unowned or unreserved item remains, a collection-complete record is stored without duplicate ownership.

Weekly Goal editing is opened from the edit icon in the Activity goal section. The Profile surface contains no goal-setting action. The annual contribution grid keeps 48dp touch cells while filling each slot with a 46dp square; the weekly widget projection uses a proportional 4% horizontal and 6% vertical inset to keep gaps compact across sizes.

## Persistence and backups

The existing Room `opus.db` remains authoritative at schema 12. Migration 11→12 adds Activity settings, weekly goals, week metadata, manual entries, cosmetic ownership, reward grants and loadout records; the prior migration chain is preserved. Backup format 7/schema 12 includes the new tables. Older readers remain. Format 7 restore validates in an isolated Room database and merges the new Activity records without replacing the legacy personal journal.

## Deferred verification and constraints

The API 37 SDK packages and host integration build are configured. API 37's large-screen orientation/resizability changes were checked against the manifest: the app does not force orientation or a fixed aspect ratio, so those platform rules do not require a manifest exception. The Activity screen was launched and inspected on API 37; responsive navigation/accessibility checks passed across 32 size/locale/theme/font combinations. Weekly RemoteViews rendering passed instrumentation across supported sizes and large fonts; actual launcher placement/resizing remains pending. Android 17 background-audio behavior still needs runtime validation for lifecycle-bound local playback and the foreground microphone service. The repository already stops local playback when Practice leaves foreground; no 0.14 audio rewrite is planned without a reproduced regression.

The source-final API 37 baseline passed 279 instrumentation tests before this UX follow-up. Its first local attempt exited 139 on the malformed Play Store AVD using `swiftshader_indirect`; Fedora coredumps and audit records tied that RenderThread SIGSEGV to an SELinux `execheap` denial, and the AVD metadata had `target=android-0`. The recovery uses the correctly configured API 37 Google APIs AVD, cmdline-tools 23.0 metadata, and headless `swangle` without weakening SELinux. The repeatable runner passed 21 focused instrumentation tests (repository/rewards/cosmetic ownership and Apply persistence, populated migration, RemoteViews, responsive accessibility) with zero failures/errors/skips; `MainActivity` launched and Activity screenshots were inspected. See [Fedora emulator diagnosis and procedure](../maintenance/ANDROID-EMULATOR-FEDORA.md). Full instrumentation, direct collection-screen Apply interaction, launcher-host widget placement/resizing, signed in-place upgrade and final APK signature/metadata/hash checks remain pending. No GitHub operation is in scope for this follow-up.

November 14 claim-flow follow-up: host domain/JVM tests, app and instrumentation compilation, and lint passed. Eleven Activity repository instrumentation tests passed on API 37, including durable pending claims, duplicate prevention, four eligible weeks, and claim persistence. The Activity goal-editor Compose semantics test passed on API 36. The same test could not start its Espresso idle assertions on API 37 because the current Espresso version cannot resolve `InputManager.getInstance`; this is recorded as a harness incompatibility. No visual or screenshot testing was performed. See the current 0.14 checklist for exact run details and limits.

The selected minSdk 30 means devices on Android 8–10 (API 26–29), supported by Gould 0.13, cannot install a 0.14 update. Their existing app/database is not reset, but they will not receive 0.14. This is the direct compatibility consequence of the agreed minimum SDK direction; release notes must state it clearly.

Discover source/routes and administration/moderation routing/security remain present while their navigation entries are hidden. Historical reports describe prior Discover repair work but do not establish a newly reproduced defect in this branch. No specific moderation runtime error is claimed. Reactivation should first validate the exact reported issue, provider-consent/cache behavior, access control and focused navigation tests.

Rust was not added. The current deterministic workload has no measured performance constraint that would justify native interop, build, ABI and maintenance overhead.
